# 灵犀 Lingxi · 人工客服的共情副驾

> 心有灵犀，一点即通。读懂消费者没说出口的那句话。

欧莱雅第二届美妆科技黑客松 · 赛题 1「数据共情者——消费者的 AI 管家」参赛作品。

灵犀不是自动回复机器人。它是嵌在现有客服工作台右侧的一个插件，坐在人工坐席身边：把聊天、订单、工单并成一条服务轨迹，读出情绪、意图和潜台词，把风险分级并给出证据，起草三版回复并在发送前做合规检查——最后发什么，由坐席决定。跨会话看，同一套引擎驱动一块风险预警跟踪看板。

对应赛题的两个产出物：

| 赛题要求 | 在哪里 |
|---|---|
| 智能接待辅助插件 | `/console` 右侧栏（可收起，收起后就是原来的工作台） |
| 风险预警跟踪看板（舆情投诉、重复进线、情绪升级、重复退款 + 状态跟踪） | `/alerts` |
| 文本聊天 + 结构化订单 + 工单的融合 | `src/lib/dataset.ts`、`src/lib/engine/journey.ts` |
| 可量化的评估标准 | `/eval`、`eval/` |
| Token 成本节约机制 | `src/lib/engine/router.ts`、`/eval` |
| 承诺与任务闭环、发送前审查 | `src/lib/server/db.ts`、`src/lib/server/gate.ts`、`/api/tasks`、`/api/send-check` |

> **数据说明**：品牌（AURELLE 等）、产品、消费者、订单、工单、批次全部为演示虚构，服务数据是按赛题描述的三类结构自建的合成数据。灵犀**没有做过任何试点**，本项目不包含任何业务效果数字。主办方的示例数据需登录报名后下载，尚未导入。

## 快速开始

需要 Node.js 22.13 或更高版本（需支持内置的 `node:sqlite`），以及 pnpm。本地已在 Node.js 25.2.1 上验证。

```bash
git clone https://github.com/wangzh12023/lingxi.git
cd lingxi
pnpm install
pnpm dev            # 开发模式，http://localhost:3000
```

正式演示建议用生产模式，更快也更稳定：

```bash
pnpm build
pnpm start          # http://localhost:3000
```

不配置任何密钥即可完整运行（离线模式，由规则引擎和演示脚本驱动）。

### 接入大模型（可选）

```bash
cp .env.example .env.local   # Windows 可直接复制文件
# 编辑 .env.local，填入 LLM_API_KEY
pnpm build && pnpm start
```

然后打开 `/settings` 点“测试连接”。默认主模型为 `qwen3.8-27b`，快速模型为 `qwen3.5-35b-a3b`，图片识别使用主模型。任何兼容 OpenAI 接口的服务都可以，修改 `LLM_BASE_URL`（通常需包含 `/v1`）和模型名即可；请先确认服务商提供对应模型。

2026-10-19 已通过兼容接口实际验证主模型分析、快速模型语义审查和图片识别，生产构建及 7 组项目检查全部通过。这些连接检查不等同于完成真实模型的整套评测。密钥仅保存在本地 `.env.local`，不会随仓库发布。

## 它是怎么工作的

每一句消费者发言都会经过同一条流水线（`src/lib/engine/pipeline.ts`）：

```
感知  忆 服务轨迹 · 望 看图 · 闻 情绪 · 问 意图与潜台词 · 切 风险
省    路由：这一轮给多少模型（0 / 1 / 2 次调用）
融合  典 检索依据 · 策 下一步行动与“灵犀一念”
起草  笔 三版回复
守护  检 合规检查与评分
```

还有四个不在每轮运行的智能体：**护**（坐席守护）、**议**（会诊主持）、**察**（数据洞察）、**练**（共情教练）。

### 三种判断来源，界面上都会标明

| 来源 | 什么时候 | 谁做判断 |
|---|---|---|
| 演示 | 剧本里的消费者发言 | 人工撰写的判断（代替大模型）|
| 规则 | 没有配置大模型，或路由判定不需要模型 | 规则引擎 |
| 模型 | 配置了大模型 | 大模型，规则引擎同时把关 |

哪些由模型判断、哪些由规则决定，分得很清楚：

- **由规则和数据决定，不取模型的数字**：审批人（按行动类型、金额和此前的履约情况，服务端计算，模型或页面送来的审批字段一律丢弃）、草稿里每个订单号、金额、时间和“已安排”是否有依据（发送前在服务端核对）、量表评分、路由、是否会诊与入席部门、服务轨迹与批次查询、知识检索。
- **风险等级：模型给出建议等级，规则命中的等级是下限；模型引用的证据在材料里找不到时，最多算 L2 并标为“待核实”；人工可以附依据纠正，纠正后不再进入分析**。
- **情绪的主导项、强度、效价和走势**由八维向量算出；向量本身来自模型或规则，所以这些数字只是对判断的汇总，不是独立的测量。
- **会诊的“模拟立场一致度”**是对一次模拟讨论里各席位表态的算术平均，不代表各部门批准，也不能证明方案安全。

### 多源融合：服务轨迹

`src/lib/dataset.ts` 是按赛题描述的三类结构自建的合成数据：进线记录（聊天原话）、订单、售后工单。`src/lib/engine/journey.ts` 按消费者把它们排成时间线，再跨源比对，得出单个会话里看不到的事实：

| 事实 | 规则 |
|---|---|
| 重复进线 | 7 天内有未解决的进线，又来了 |
| 重复退款 | 90 天内退款工单达到 3 张 |
| 承诺逾期 | 工单承诺的期限已过仍未关闭 |
| 情绪升级 | 最近 3 次进线的情绪效价逐次下降，且最后一次低于 −0.4 |

这些事实既出现在插件的“忆 · 服务轨迹”里，也驱动 `/alerts` 的预警（`src/lib/alerts.ts`）。

### 省 token：先让规则读一遍

规则引擎本来就要运行（它是护栏）。`src/lib/engine/router.ts` 用它的读数决定这一轮给多少模型：

| 路由 | 调用 | 什么时候 |
|---|---|---|
| 规则直达 | 0 次 | 寒暄、致谢、确认 |
| 轻量 | 1 次，快速模型 | 规则有把握的低风险咨询：快速模型一次完成复核与起草；它发现风险就升级到完整路由 |
| 完整 | 1 次，主模型（核验不通过时再修正 1 次） | 有风险、有负面情绪、有图片、业务数据里有异常，或规则读不懂 |

路由只在规则确实认出来的时候才往下放，而且只有寒暄不经过任何模型。主模型每轮只调用一次，同时完成研判与起草；系统核验草稿，只有发现无依据或违规的说法才带着原因交回模型修正一次（生成 → 核验 → 修正）。和合理的“单次调用 + 基础检索”基线相比，估算的 token 基本持平、费用略低（见 `/eval`）；只和“每个智能体各调用一次”比才会少很多，那个对比不作为卖点。另外：评分与合规不问模型；对百炼的调用关闭思考模式；提示词按“档案 → 对话 → 本轮内容”排列（`src/lib/engine/context.ts`），让同一会话的前后调用共享前缀，方便服务商的前缀缓存命中。接入真实密钥后，每次调用的 token、耗时和缓存命中量显示在插件的“执行轨迹”里。

### 记住经历、兑现承诺

这是本作品最想证明的一件事。

- **事实包**（`src/lib/engine/facts.ts`）：订单、工单、每一次答应过消费者的事（含重申记录）及是否兑现、消费者已经提供过的东西、在办任务。服务端按消费者 ID 构建，模型和规则都用它。
- **逐句核对**（`src/lib/engine/claims.ts`）：回复里的订单号、金额、具体时间、“已为您安排”、补偿和政策用语，都要在事实包、已提交的任务或适用的条款里找到依据，否则拦下。
- **任务闭环**（`src/lib/server/db.ts`，Node 自带的 SQLite）：提出 → 按权限审批 → 提交模拟工单 → 登记结果 → 到期回访 → 闭环或重新打开。只有拿到工单号才算“已安排”；每一步留下操作人、时间和幂等键；刷新、换坐席后仍在。
- **发送前审查**（`src/lib/server/gate.ts`）：按发送键时服务端审查确切的这段文本，改一个字就要重审；L3 以上的会话没有模型复核时，需组长过目后发送。
- **风险事件**（`src/lib/events.ts`）：风险按事件合并与跟踪；闭环后有新证据会重新打开；人工可附依据纠正，纠正后不再进入分析。

主演示“算了，你们每次都说明天”：系统查出同一件事答应过三次，回复先承认失约、不再给口头时间；补寄申请要组长批准，批准后生成工单号，回复才说“已为您提交”；换一位坐席接手看到的是同一个工单；演示时钟推到期限之后，看板和插件都提示“到期未兑现”。浏览器走查：`node scripts/walk-promise.mjs`。

### 一些设计上的取舍

- **风险会累积**：一次会话里识别到的风险不会因为对方语气缓和就消失。
- **舆情看时态**：“我已经发小红书了”是已公开，“再不处理我就发”是威胁，“在小红书上种草的”什么都不是。
- **症状词不等于症状**：“会不会过敏”“我酒精过敏”“朋友说她用了过敏”都不是不良反应报告（`eventText`）。
- **法定时限用原文**：不良反应一般 30 日、严重 15 日、可能引发较大社会影响 3 日内报告（《化妆品不良反应监测管理办法》第二十三条）。界面上的“24 小时”是演示品牌的内部规范，已标明。
- **批次预警是真算的**：输入的投诉数是模拟的，但泊松检验、预警阈值、预警时间都是计算出来的（`src/lib/insights.ts`）。
- **会诊按归属入席**：产品安全请质量与研发，舆情请公关与法务，流失请会员运营，异常索赔请风控。面板先给决策简报；讨论是一次生成的多角色模拟，“模拟立场一致度”不代表批准；决议可转为待主管批准的任务。
- **评分可以解释**：每一分都能拆回到具体的检查项。工作台和共情学院用同一套量表。
- **图片默认模糊**：识别之前整张模糊；识别后遮住眼部等隐私部位；没有视觉模型时保持模糊，提示人工查看。
- **出错不中断**：模型超时或返回格式不对时，该智能体由规则接替，星图上标为“已降级”。

## 评测

```bash
pnpm check                    # 全部检查（7 组）
npx tsx eval/run.mts          # 组件评测：意图、情绪、风险类别、回复拦截
npx tsx eval/run.mts --llm    # 同上，加上已配置的大模型（消耗 token）
pnpm eval:e2e                 # 端到端评测：产品流水线跑多轮会话 + 服务历史（规则条件）
pnpm eval:e2e --llm           # 五个条件：规则、基线、基线 + 事实、完整灵犀、灵犀不路由
```

结果写入 `eval/results.json`、`eval/e2e-results.json`，逐轮记录写入 `eval/runs/`；`/eval` 页面从这些文件读数。

| 数据 | 用途 |
|---|---|
| `eval/dataset.ts` | 调参集，开发者撰写。规则照着它改，分数不作数 |
| `eval/round1.json` | 第一轮留出集的成绩，冻结 |
| `eval/blind/`、`blind-texts/` | 迭代验证集：独立标注者撰写、第二位盲标复核。规则没有据它调整，但路由据它的一个汇总数字改过一次，所以不称盲测 |
| `eval/final/` | **最终测试集**：新的独立标注者撰写，2026-10-14 冻结（`FROZEN.json` 记录哈希，被改动则评测拒绝运行）。主结果都在它上面 |
| `eval/e2e-first.json` | 最终测试集上端到端评测（规则条件）的第一次运行，冻结 |
| `eval/human-review/` | 人工复核用的表格与说明 |

所有标注者都是大模型，没有人工裁决；评测文本不是真实消费者语料。来历和提示词原文见 `eval/PROVENANCE.md`。

## 还没有做到的

- 没有试点，没有业务效果数据。
- 已验证真实模型连接和关键调用链路，尚未完成真实模型的整套评测；评测页的模型成绩仍标“未测”。
- 工单系统是模拟的；审批和身份是演示用的人员名单，没有登录。
- 批次异常的统计输入仍是合成的统计表，还没有改为从事件动态聚合。
- 服务数据是合成的；主办方的示例数据尚未导入。
- 盲测集由 AI 标注；token 节省是按提示词长度的估算。
- 演示剧本的判断由人撰写；两张演示插画的识别结果是预置的。
- 洞察页数据是模拟的；话题聚类是预置结果，没有实现聚类算法。
- 作业规范、售后政策、产品资料是为演示写的。五篇法规文档里的条文逐字摘自官方文本（2026-10-12 核对），但“怎么用”是我们的理解，正式使用前需要法务审核。
